# Replit Prompt 1 — Backend: Schema, Auth, Routes, Seed

## Context

This is v2.1 of the IQmeetEQ Workshop Companion App. The existing v1.0 app is a working pnpm monorepo with this structure:

```
artifacts-monorepo/
├── artifacts/
│   ├── api-server/         # Express 5 API server
│   └── workshop/           # React + Vite frontend
├── lib/
│   ├── api-spec/           # OpenAPI spec + Orval codegen config
│   ├── api-client-react/   # Generated React Query hooks
│   ├── api-zod/            # Generated Zod schemas from OpenAPI
│   └── db/                 # Drizzle ORM schema + DB connection
```

Stack: Express 5, PostgreSQL + Drizzle ORM, Zod validation, cookie-session, Node 24, TypeScript 5.9, esbuild CJS bundle.

v2.1 adds a **cohort system** — each workshop gets its own virtual instance of the app. This prompt covers the entire backend: new database schema, rewritten auth, all API routes (participant + admin), and the seed script. Do NOT touch any frontend code in this prompt.

## 2. Auth Routes

Rewrite `artifacts/api-server/src/routes/auth.ts`:

### POST /auth/login

Request body: `{ email: string, cohortCode?: string }`

Flow:
1. Validate email format (same as v1.0)
2. Normalize email to lowercase/trimmed
3. Check if this email already exists in `participants`:
   - **If exists AND has a cohort_id:** This is a returning participant. Update `lastLoginAt`. Set session. Return participant with `isNew: false`. Ignore any `cohortCode` in the request — they're already bound.
   - **If exists AND cohort_id is null:** This is a participant from before cohorts existed (shouldn't happen in fresh deploy, but handle it). If `cohortCode` is provided, look up the cohort, bind them. If no `cohortCode`, return error "Cohort code required."
   - **If NOT exists:** This is a new participant. `cohortCode` is required. Look up cohort by `cohort_code` (case-insensitive). If not found, return 400 `"Cohort code not recognized."` If found, create participant with `cohort_id`, set session, return with `isNew: true`.
4. Session stores: `participantId` and `cohortId`

### GET /auth/me

Same as v1.0 but also return the participant's cohort info (name, facilitator_message, tier_access). Join participants with cohorts.

### POST /auth/logout

Same as v1.0.

## 3. Sections Routes

Rewrite `artifacts/api-server/src/routes/sections.ts`:

Keep the `ALL_SECTIONS` array as-is — it's the master list of hardcoded sections. But the API responses are now scoped to the participant's cohort.

### GET /sections

1. Get participant's `cohort_id` from session
2. Query `cohort_sections` for that cohort, joined with the `ALL_SECTIONS` data and any `generic_sections`
3. For generic sections (section_id starts with "generic_"), fetch title/type from `generic_sections` table
4. Return sections ordered by `level` then `sort_order`, filtered to `visible = true`
5. Each section includes: id, title (use `display_name` if set, else default), description, level, sort_order, type, unlocked status, hasCode
6. Unlocked status: check `unlocked_sections` for this participant. Sections in levels where `tier_access` is true are automatically unlocked.

### POST /sections/unlock

1. Get participant's `cohort_id` from session
2. Look up the code in `cohort_sections` WHERE `cohort_id` = participant's cohort AND `code` (case-insensitive) AND `code_active = true`
3. May match multiple rows (one code unlocking multiple sections)
4. Insert into `unlocked_sections` for each matched section (skip if already unlocked)
5. Return the first matched section's info

## 10. Admin Routes

Rewrite `artifacts/api-server/src/routes/admin.ts`. Keep `requireAdmin` middleware and the admin login/logout. Replace everything else:

### Cohort Management

**GET /admin/cohorts** — List all cohorts, ordered by created_at DESC

**POST /admin/cohorts** — Create cohort. Body: `{ name, audience_type, cohort_code, facilitator_message?, tier_access? }`. On creation, auto-populate `cohort_sections` with ALL_SECTIONS in default order (all Level 1 sections with their default codes from `SECTION_CODE_CONFIG`, Level 2/3 sections visible but no codes).

**PUT /admin/cohorts/:id** — Update cohort settings (name, audience_type, cohort_code, facilitator_message, tier_access, settings)

**GET /admin/cohorts/:id** — Get single cohort with full details

### Per-Cohort Section Management

**GET /admin/cohorts/:cohortId/sections** — Get all cohort_sections for this cohort, joined with section details (from ALL_SECTIONS or generic_sections). Ordered by level, sort_order.

**PUT /admin/cohorts/:cohortId/sections** — Bulk update section ordering. Body: array of `{ section_id, level, sort_order, display_name?, visible, code?, code_active }`. Replaces all cohort_sections for this cohort.

**POST /admin/cohorts/:cohortId/unlock-all** — Unlock all sections for all participants in this cohort. Inserts into `unlocked_sections` for every participant × every visible section in this cohort. Skips already-unlocked.

### Content Variants (Admin)

**GET /admin/cohorts/:cohortId/variants** — Get all content variants for this cohort

**PUT /admin/cohorts/:cohortId/variants** — Upsert a content variant. Body: `{ section_id, block_key, content }`. If content is empty string, delete the variant (revert to default).

### Generic Sections

**GET /admin/generic-sections** — List all generic sections

**POST /admin/generic-sections** — Create. Body: `{ title, content, prompt_block?, goal_text?, section_type }`. Returns the created section with its ID.

**PUT /admin/generic-sections/:id** — Update

**DELETE /admin/generic-sections/:id** — Delete (also removes from any cohort_sections referencing it)

### Safari Library

**GET /admin/safari-library** — List all Safari tools with their files

**POST /admin/safari-library** — Create tool. Body: `{ name }`

**PUT /admin/safari-library/:id** — Update (name, sort_order, active)

**DELETE /admin/safari-library/:id** — Delete tool (also removes from cohort_safari_tabs and related files)

### Cohort Safari Tabs

**GET /admin/cohorts/:cohortId/safari-tabs** — Get Safari lineup for this cohort, joined with safari_library details

**PUT /admin/cohorts/:cohortId/safari-tabs** — Set Safari lineup. Body: array of `{ safari_library_id, sort_order }`. Replaces all cohort_safari_tabs for this cohort.

### LLM Tools (Admin)

**GET /admin/llm-tools** — List all (same as public but includes inactive)

**POST /admin/llm-tools** — Create. Body: `{ name, display_label, url }`

**PUT /admin/llm-tools/:id** — Update (name, display_label, url, active, sort_order)

**DELETE /admin/llm-tools/:id** — Delete

### Feedback Categories (Admin)

**GET /admin/feedback-categories** — List all

**POST /admin/feedback-categories** — Create. Body: `{ name }`

**PUT /admin/feedback-categories/:id** — Update (name, sort_order, active)

**DELETE /admin/feedback-categories/:id** — Delete

### App Settings (Admin)

**GET /admin/settings** — Get all settings

**PUT /admin/settings** — Upsert. Body: `{ key, value }`. Updates if key exists, inserts if not.

### Participant Management

**GET /admin/cohorts/:cohortId/participants** — Same engagement data as v1.0 but filtered by cohort

**PATCH /admin/participants/:id/active** — Same as v1.0

**DELETE /admin/participants/:id** — Delete participant and all their data (notes, unlocked sections, workflow maps, feedback). Confirmation happens on frontend.

### Feedback Review (Admin)

**GET /admin/feedback** — All feedback across all cohorts. Supports query params: `?cohort_id=X&category=Y&sort=date`. Returns feedback with participant email and cohort name joined.

### File Management

Keep existing file upload/download/delete routes but update to use `safari_library_id` instead of `tool_tab` for Safari file assignments.

## 14. Important Patterns to Preserve

- Use Zod validation on all request bodies (create schemas in api-zod or inline)
- Use `req.session?.participantId` for participant auth, `req.session?.isAdmin` for admin auth
- Use `res.set("Cache-Control", "no-store")` on GET endpoints that return user-specific data
- All timestamps use `timestamp("column_name").defaultNow()`
- Use `returning()` on all INSERT/UPDATE operations
- Keep the logger (`pino`) usage pattern
- Express 5 async error handling (no need for try/catch wrappers in Express 5)
