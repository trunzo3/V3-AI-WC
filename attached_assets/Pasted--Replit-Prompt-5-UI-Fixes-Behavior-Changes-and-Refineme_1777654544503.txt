# Replit Prompt 5 — UI Fixes, Behavior Changes, and Refinements

## Context

Prompts 1–4 built the full v2.1 app: cohort system, participant UI, admin panel, and PDF export. This prompt is a cleanup pass — 15 fixes and refinements. None are architectural changes. All use existing tables, routes, and infrastructure.

---

## 1. Admin Login Consolidation

**Current:** Two admin login experiences — a gear icon on the participant login page shows an inline password-only form (white/light theme), and `/admin/login` shows a separate page with email + password (dark theme).

**Fix:** Remove the inline admin form from the participant login page. The gear icon should navigate to `/admin/login` instead of toggling an inline form. Keep the gear icon (subtle, bottom-left) but make it a link, not a toggle. The only admin login is `/admin/login` with both email and password fields, dark theme. Remove all inline admin auth code from the participant login component.

---

## 2. Generic Section — Rich Text Editor

**Current:** The "Body content" field in the generic section admin form is a plain `<textarea>`. Pasting formatted text (bold, bullets) from a browser or document strips formatting.

**Fix:** Replace the body content textarea with a WYSIWYG rich text editor. Use a lightweight library — `@tiptap/react` with the starter kit is ideal (headings, bold, italic, bullet lists, ordered lists, links, code blocks). If tiptap is too heavy, use `react-quill` or `suneditor-react`. The editor should:
- Accept pasted formatted text and preserve bold, italic, bullets, links
- Store the content as HTML in the database (the `content` column in `generic_sections`)
- On the participant side, the `GenericSectionView` component already uses `dangerouslySetInnerHTML` — it should render the HTML correctly once the content is actually HTML instead of plain text

Also apply the same WYSIWYG treatment to the **facilitator message** editor in the cohort edit form, since that also renders as HTML on the vestibule.

Install the editor library:
```bash
pnpm --filter @workspace/workshop add @tiptap/react @tiptap/starter-kit @tiptap/extension-link
```

## 3. Code Toggle Behavior Fix

**Current:** The "Code on" toggle in the Sections tab is confusing. When toggled off, the section still appears but with a bubble icon and no way to unlock it.

**Fix:**
- Rename the toggle label from "Code on" to "Requires code"
- When "Requires code" is ON: the section is locked and requires the specified code to unlock. Lock icon in sidebar.
- When "Requires code" is OFF: the section is automatically unlocked for all participants — no code needed. It appears as an open/accessible section in the sidebar immediately. No lock icon, no bubble icon.
- This behavior applies identically to Level 1, Level 2, and Level 3 sections. The cohort's tier access setting ("Open levels") controls whether a level is accessible at all. The "Requires code" toggle controls whether individual sections within an accessible level need a code.
- Backend: when a section has `code_active = false` (Requires code OFF), the `GET /sections` endpoint should return it as unlocked regardless of whether it exists in `unlocked_sections`. No code entry needed.
- Sidebar icons: use a lock icon (🔒) for locked sections, a gold filled circle for unlocked sections that have notes, and an empty circle for unlocked sections without notes. Remove any "bubble" icon state.

**Fix:** The workshop code field must be empty by default. Use placeholder text only (gray hint: "Enter workshop code"). No pre-filled value. The field should never auto-populate with any cohort code on initial page load.

## 6. Returning Participant Login Flow

**Current:** Returning participants must re-enter their name and workshop code every time. If they don't enter their name, it defaults to the part before @ in their email.

**Fix:** Change the login flow for returning participants:

1. **First visit:** Show three fields — Workshop Code, Name, Email, Confirm Email. All required.
2. **Return visit:** Show one field — Email. When the participant enters their email and it matches an existing account:
   - Pre-fill the Name field with their stored name (shown but editable — they can change it if they want)
   - Hide the Workshop Code field entirely (they're already bound to a cohort)
   - Show a small "Switch workshop" link below the email field. Clicking it reveals the Workshop Code field for the rare case where someone needs to join a different cohort.
   - Auto-detect returning vs. new: after email is entered (on blur or on submit), check if the email exists via the backend. If exists, collapse to the returning flow. If new, show the full form.

3. **Backend change:** The `GET /auth/me` or a new lightweight `POST /auth/check-email` endpoint should return whether an email exists and, if so, the participant's name — without creating a session. This lets the frontend know to show the returning flow before the user submits.

## 7. Cohort Deletion

**Current:** No way to delete cohorts from the admin panel.

**Fix:** Add a delete button (red trash icon) to each cohort card in the Cohorts tab. Clicking it opens a confirmation dialog:
- Dialog text: "Permanently delete [Cohort Name]? This will remove all section mappings, Safari lineup, and content variants for this cohort. Participant data (notes, workflows, feedback) will NOT be deleted."
- The dialog has a text input: "Type DELETE to confirm"
- The delete button in the dialog is disabled until the user types "DELETE" (case-sensitive)
- On confirm: call `DELETE /admin/cohorts/:id` (create this endpoint if it doesn't exist)
- Backend deletes: the cohort row, all `cohort_sections` rows for that cohort, all `cohort_safari_tabs` rows, all `content_variants` rows for that cohort
- Backend does NOT delete: participants, notes, unlocked_sections, workflow_maps, or feedback
- After deletion: if the deleted cohort was the currently selected cohort in the admin switcher, switch to the first available cohort (or show "No cohorts" state)
- Refresh the cohort list after deletion

Remove the old "Safari library" and "Safari lineup" tabs from the tab bar.

## 9. Safari File Upload

**Current:** The Safari Library shows tools with name, sort order, and active status, but no way to upload PDF guides.

**Fix:** Add file management to each tool in the Safari Library section:
- Each tool card gets a "Files" button or expandable area
- Clicking it shows:
  - List of uploaded files for that tool (filename, size, download link, delete button)
  - Upload button: "Upload Guide (PDF)"
- Upload uses the existing file upload infrastructure: `POST /admin/files` with `{ displayName, mimeType, fileData (base64), sectionId: "tool-safari", safariLibraryId: [tool id] }`
- Download uses existing: `GET /api/files/:id/download`
- Delete uses existing: `DELETE /admin/files/:id`
- On the participant side, the Tool Safari component should show a "Download Safari Guide (PDF)" button for each tab that has an uploaded file, using the file associated with that tool's `safari_library_id`

## 13. LLM Tool Pills in Sidebar

**New feature:** Add quick-access links to LLM tools in the sidebar, pinned below the "← Home" link and above the scrolling section list.

**Layout:**
```
← Home

[Gemini] [ChatGPT] [Claude] [Copilot]

▾ LEVEL 1 — CORE WORKSHOP    5/18
  Verification Test
  Tool Safari
  ...
```

**Implementation:**
- Fetch the LLM tools list from `GET /llm-tools` (same endpoint used by the Verification Test)
- Display each active tool as a small pill/chip: background `#E8E4DC`, navy text, 11px font, font-weight 600, border-radius 20px, padding 4px 10px
- Each pill is an `<a>` tag with `target="_blank"` — clicking opens the tool URL in a new tab
- The Home link + pills area is pinned (doesn't scroll). The section list below scrolls independently.
- If no LLM tools are configured, don't show the pills area — just show "← Home" and the section list

**Styling:**
- Wrap Home + pills in a `position: sticky; top: 0` container (or equivalent for the sidebar's scroll container)
- Add a subtle bottom border or shadow to separate the pinned area from the scrolling list
- Pills wrap to a second row if there are too many (flex-wrap: wrap)
